# 商奕前端类型化与构建可行性评估

- 版本：v0.1
- 日期：2026-10-04
- 评估对象：`shangyi/sidecar/web/`（约 2730 行手写 JS，零构建、零安装）
- 结论一句话：**采纳 TypeScript 检查器，但不引入构建链。** 二者不是一回事，本文用实测数据把它们拆开。

---

## 0. 结论摘要

| 提案 | 结论 | 一句话理由 |
| --- | --- | --- |
| 引入 **TypeScript 类型检查** | ✅ **采纳** | 用 `// @ts-check` + `--noEmit` 落地，**不需要构建步骤、不改一行业务代码** |
| 引入 **构建链**（esbuild / Vite / Rollup） | ❌ **不采纳** | 实测无任何收益支撑：产物是 localhost 静态文件，依赖已 vendor，代码量未到需要打包的临界点 |
| 引入 **React + `motion/react`** | ❌ **不采纳** | 需重写全部 10 个视图；换来的能力在本地控制台场景用不上 |

核心区分：

- **类型检查** = 一个 linter。`tsc --noEmit` 产出零字节文件，Node 与浏览器仍直接执行原 `.js`。
- **构建** = 一个编译器。产出新文件，改变分发方式，需要 Node 才能跑起来。

商奕目前缺的只是前者。**把前者当后者来买，是这次评估要避免的主要浪费。**

---

## 1. 评估方法

拒绝「凭经验判断」，全部结论来自对当前代码**零改动**运行的实测。

工具链：

- TypeScript **7.0.2**（原生 Go 编译器，2026-10 时点最新版）
- 配置文件 `allowJs` + `checkJs` + `noEmit`，目标 ES2022 / DOM
- 被测对象：全部 17 个 `js/**/*.js`（2730 行），**未修改任何一行业务代码**

> 行数含本轮新增的 `js/motion.js`（动效封装，约 190 行）；基线测量在该文件加入之后进行，因此下列数据与当前工作区一致。

## 2. 实测数据

### 2.1 基线：当前代码有没有类型问题？

```
tsc --allowJs --checkJs --noEmit（strict: false）
→ 46 个错误
```

按错误码归类：

| 错误码 | 数量 | 含义 |
| --- | --- | --- |
| `TS2339` | **46 / 46（100%）** | Property does not exist |

**46 个错误全部是同一类噪声**：代码写 `document.querySelector('#x').value`，而 `querySelector()` 的静态返回类型是 `Element`，`Element` 上没有 `value`。

按属性统计：

| 属性 | 次数 | 实际元素类型 |
| --- | --- | --- |
| `.value` | 37 | `HTMLInputElement` / `HTMLTextAreaElement` |
| `.disabled` | 4 | `HTMLButtonElement` |
| `.onclick` / `.dataset` / `.open` / … | 5 | 各有对应元素类型 |

**这 46 个错误没有一个是真 bug。** 浏览器运行时行为完全正确，它们纯粹是「选择器返回的元素类型比检查器知道的更具体」。

> **重要判断：TypeScript 在 2730 行现有代码里发现 0 个真实缺陷。**

### 2.2 加强检查：开 `strict` 呢？

这是对「引入 TS」最强的支持性检验——如果严格模式能挖出真 bug，就该采纳。实测：

```
tsc --strict --allowJs --checkJs --noEmit
→ 690 个错误
```

归类：

| 类别 | 数量 | 是否真实缺陷 |
| --- | --- | --- |
| `TS7006/7005/7053/7034/7031/7023`「隐式 any」 | **516** | 否。这不是 bug，是「还没写注解」 |
| `TS2339` DOM 收窄 | 66 | 否，同 2.1 |
| `TS2531/TS18047/TS18046` 可能为空 | **108** | 否。全部是 `getElementById` / `querySelector` 取静态 HTML 中的固定节点，实际永不为 null |

抽查全部 108 个 nullability 报错，宿主变量都是同一个：

```
js/app.js(14,69): 'host' is possibly 'null'
js/app.js(34,45): 'host' is possibly 'null'
js/app.js(35,2):  Object is possibly 'null'
```

`host` 来自 `index.html` 里写死的 `<div id="view">`，永远存在。

> **结论：`strict` 的 690 个错误衡量的是「要写多少注解」，不是「有多少潜在 bug」。**
> 0 个真实缺陷——因为代码里根本没有类型可以对照，全都是 `any`。

### 2.3 哪些文件本来就干净？

逐文件检查（非严格模式），结果分成两半：

| 状态 | 文件数 | 文件 |
| --- | --- | --- |
| ✅ **零错误** | **9** | `components.js` `guide-state.js` `markdown.js` `motion.js` `research.js` `ui.js` `util.js` `views/overview.js` `views/playground.js` |
| ❌ 有 DOM 噪声 | 8 | `api.js` `app.js` `views/activity.js` `views/case.js` `views/cases.js` `views/chat.js` `views/guide.js` `views/run.js` |

**超过一半的文件今天就能开类型检查，一行代码都不用改。**

而且 8 个「不干净」文件的错误**同根同源**，全部是 `querySelector()` 返回 `Element`（见 2.1）。没有第二种成因。

### 2.4 手工维护的联合类型有多少？

TS 最强的卖点是把联合类型交给编译器。项目里确实有手写收窄：

```js
// js/views/cases.js:33
const results = await Promise.allSettled([api.cases(), api.chats()]);
if (results.every(r => r.status === 'rejected')) throw new Error(...);
const cases = mergeConsultations(results[0].value?.cases || [], ...);
```

`Promise.allSettled` 返回的是可辨识联合 `PromiseSettledResult<T>`，`.value` 只在 `status==='fulfilled'` 分支存在。代码用手工 `status` 判断做了正确收窄，但**这个约束没有被编译器记住**——判定写在 `r` 上，访问发生在 `results[0]` 上。

全项目分布：**3 个文件**（`app.js`、`views/activity.js`、`views/cases.js`），5 处未收窄的 `.value` 访问。

另有 `README.md` 已明文记录的一处形状不唯一：

```js
// js/views/case.js:81 —— gamespec 可能直接是参数，也可能在 spec 包装内
const spec = data.artifacts?.gamespec?.spec || data.artifacts?.gamespec || {};
```

以及 `case.js:82` 的 `report?.report?.ledger || report?.ledger`。全项目同类兜底链 **3 处，集中在 1 个文件**。

> 这不是系统性问题，但它是**类型真正能买到东西的地方**——在 API 边界，而不是 DOM。

### 2.5 验证机制本身有效吗？

「当前没 bug」有两种可能：(a) 代码确实干净；(b) 检查器根本没在工作。必须排除 (b)。

构造两个对照文件，只加 JSDoc 注解，不做任何编译：

```js
// @ts-check
/** @param {{n?:number}} o */
export function count(o) {
  return o.n_events;   // 打错字：应为 n
}
```

```
→ error TS2339: Property 'n_events' does not exist on type '{ n?: number | undefined; }'
```

```js
// @ts-check
/** @param {{stats?:{n_events?:number}}} data */
export function row(data) {
  return data.stats.n_events;   // stats 可能为 undefined
}
```

```
→ error TS18048: 'stats' is possibly 'undefined'
```

**检查器确实在抓真错**（拼写错误、可空性）。结论 2.1 的「0 个真实缺陷」不是因为检查器失灵。

## 3. 建议方案：只加检查器，不加构建

### 3.1 核心机制

```
// @ts-check     ← 文件顶部一行注释，运行时零影响
```
配合
```jsonc
{"compilerOptions":{"allowJs":true,"checkJs":true,"noEmit":true, ...}}
```

关键在 `--noEmit`：

- **不产出任何文件**，仓库里不会出现编译产物
- `.js` 仍是浏览器和 `node --test` 直接执行的源文件
- 现有分发方式**完全不变**：`python3 shangyi/sidecar/web_console.py` 一条命令
- 不需要 Node 参与运行期，只需要开发期跑一次检查

`@ts-check` 是注释，所以加它**不可能破坏运行时行为**——这一点比任何推理都强。

### 3.2 阶段一（已实测验证，零业务代码改动）

实测结果：**46 个错误全部落在未加 `@ts-check` 的 8 个文件里；9 个目标文件零错误。**

需要做的事只有三件：

1. `web/tsconfig.json`（约 12 行）
2. 9 个文件顶部各加一行 `// @ts-check`
3. 一个检查脚本

> **实施补充**：随后把 `js/api.js` 也加入了检查集——它零 DOM、且是 API 边界，
> 实测能直接抓到方法名打错。详见 §3.4。当前已加入 **10 个**文件。

新增检查脚本，沿用 `tools/` 既有命名（`kb-lint.py`、`cost-report.py`）：

```
tools/typecheck.py      # 跑 tsc --noEmit，失败则退出码非 0
```

**不需要改任何一行业务代码。**

### 3.3 阶段二：**不建议做**（2026-10-04 修订，原文推荐 A，现撤回）

> **修订说明**：本文初稿推荐方案 A。实施阶段一后经进一步实测，**撤回该推荐**，改为建议不做。原因见下。

要消灭剩余 46 个 DOM 噪声，曾考虑两条路：

| 方案 | 做法 | 实测剩余错误 |
| --- | --- | --- |
| A. 统一取值助手 | 新增 `js/dom.js`，导出 `el(root, sel)` / `els(root, sel)`，JSDoc 标 `@returns {any}` | 46 → 40 |
| B. 逐点 cast | 每个 `.querySelector()` 调用点加 `/** @type {HTMLInputElement} */` | 40 → 0，但需改 46 处 |

**两条都不做。** 撤回推荐 A 的理由：

1. **`@returns {any}` 把类型收益还回去了。** 收口之后 DOM 部分仍然是 `any`，净收益只剩那 40 个 API 边界问题——而这 40 个问题**不依赖方案 A 就能拿到**：真正值得检查的 `js/api.js`（77 行、零 DOM）本来就不在这 46 个错误里。方案 A 花了 46 处改动，没买到本可以免费拿到的东西。
2. **风险落在最不该碰的代码上。** 46 个调用点分布在 `chat.js`（滚动锚定 `preserveScroll`）、`case.js`（报告渲染）、`run.js`、`guide.js`。这是一个金融决策工具的核心展示层，改错一处的代价远高于类型检查的收益。
3. **实测证明检查器本来就抓不到这里的噪声。** 构造探针验证，`api.caes()`（方法名打错）、`api.case()` 参数个数不对、`api.stopChat()` 少传参数——**三类全部被捕获**，`noImplicitAny: false` 并不会削弱检查能力。DOM 收窄那 46 条是纯噪声，清不清都不影响它抓真错。

**正确做法**：让剩余 8 个文件留在未加入状态。等到某个文件被大改时，顺手加 `// @ts-check` 再看报什么——那是自然的改动时机，不必专程做一次 46 点的重构。

### 3.4 `js/api.js`：应当加入（实施阶段新增）

`api.js` 是 77 行、**零 DOM 访问**的 API 边界，且实测证明类型检查在它上面能直接抓到方法名打错、参数个数不对。已加入检查集（连同 `status` 的一处显式类型），无 DOM 噪声要清。

**但不要给它手写响应体 typedef。** 响应结构由 Python 侧 `web_console.py` 决定；在 JS 里手抄一份就是制造第二个事实来源，必然随接口演进而失配。当前 `req` 返回 `Promise<any>` 是有意为之。

### 3.5 阶段三（明确不做）

以下内容**不在本次范围内**，写在这里是为了让后来者别重新提一遍：

- 迁移到 `.ts` 文件并重写
- 引入 React / Vue 等框架
- 打包、压缩、代码分割
- 引入 npm 运行时依赖（第三方库继续走 `web/vendor/` 随附）

## 4. 为什么否决构建链

构建链的收益，逐条对照商奕的实际情况：

| 构建链通常带来 | 商奕的情况 |
| --- | --- |
| 打包压缩、体积变小 | **不需要**。产物由 `web_console.py` 从本地磁盘读出；`web_console.py:948` 明写「静态资源不缓存——改版后刷新即生效」，带宽从来不是目标 |
| 从 npm 引入依赖 | **已解决**。第三方库按既有约定 vendor 进 `web/vendor/`（Tabler、Motion），连 MIT 许可都随附 |
| HMR 热更新 | **收益极小**。2730 行，改前端只需刷新浏览器，连后端服务都不用重启 |
| TypeScript 编译 | **`--noEmit` 已覆盖**，这是检查器不是构建器 |
| 模块别名 / 路径解析 | **用不上**。13 个文件全是相对路径，无一例外 |

反过来，构建链的代价是**永久且不可逆**的：

1. 分发方式从 `python3 shangyi/sidecar/web_console.py` 变成「装 Node → 装依赖 → 构建 → 运行」，**每个后来者都要付**
2. 引入 `node_modules` 与锁文件，与 `Cargo.lock` 并列成为第二套需要维护的依赖锁
3. 构建产物需要 `.gitignore` 纪律，否则污染仓库
4. `web_console.py` 现在直接读源文件；引入构建后，「改完刷新不生效」将成为一类新 bug

> 这条否决意见与 `web/README.md`《前端依赖策略》一节同源：当前代码量（2730 行、最大文件 534 行、0 个 TODO/HACK）**尚未触及需要构建链的临界点**。没有数据支撑的复杂度，不应该被引入。

## 5. 风险与回退

| 风险 | 概率 | 影响 | 缓解 |
| --- | --- | --- | --- |
| `tsc` 误报导致噪音疲劳，最终不看检查结果 | 中 | 高（等于没加） | 阶段一只开 9 个干净文件；DOM 噪声用方案 A 收口而非逐点 cast |
| `@ts-check` 阻碍后续重构 | 低 | 低 | 它是注释，随时可删；单文件删一行即恢复 |
| 检查脚本让 CI 变慢 / 变脆 | 低 | 低 | 当前仓库**无 CI**；先作本地脚本，不接流水线 |
| npm 缓存权限问题（本机实测遇到 `EPERM`） | 中 | 低 | 检查脚本允许 `TS_BIN` 覆盖，或提示全局安装的 `tsc` |

**回退成本：删除 9 行 `@ts-check` + 一个 tsconfig + 一个脚本。** 无编译产物、无数据迁移、无接口变更，完全可逆。
