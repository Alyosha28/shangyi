## 1. 项目概述

### 1.1 一句话定位

**商奕**是一个垂直于企业决策领域的对话式 AI Agent（对标 Codex / Claude Code 的产品形态，但领域垂直到商业决策咨询）：基于博弈论理论体系但不限于博弈论，为中小企业（欢迎大企业）在市场分析、微观经营决策、竞争对手研判、上下游关系管理等场景中，提供 **eval（评估）→ prediction（预测）→ recommendation（建议）** 的全流程分析，交付图文并茂、博弈论小白可读的咨询报告。

### 1.2 目标用户与场景

| 维度 | 设定 |
|---|---|
| 主要客户 | 中小企业主/经营者（无战略部、不懂博弈论）；大企业为高价值延伸客群 |
| 决策场景 | ① 调价/促销等微观决策 ② 竞对动向研判 ③ 市场进入/扩张 ④ 供应商/渠道谈判 ⑤ 客户关系与大客户依赖 |
| 数据假设 | 以公开数据 + 公开数据挖掘为主，用户自有数据（如有）为辅 |
| 交付形态 | 交互式 CLI 咨询过程 → 图文并茂咨询报告（PDF/docx） |

### 1.3 核心差异化（也是比赛技术创新叙事）

**解决多重均衡下博弈模型预测能力缺乏的问题。** 经典博弈论在多均衡博弈（尤其重复博弈，Folk 定理保证均衡无穷多）面前只能给出"都是均衡"，预测力归零。商奕的三层架构：

1. **Eval**：枚举完整均衡解集（含精炼过滤）
2. **Prediction**：均衡选择引擎为每个候选均衡赋"出现概率"（风险占优、随机稳定演化仿真、学习模型、QRE/level-k 行为校准、LLM 聚点判断、persona 仿真，多判据融合）
3. **Recommendation**：结合用户偏好输出对策 + 稳健性分析（结论翻转阈值）

并以**案例库回测闭环**持续校准选择判据权重——把均衡选择从艺术变成可校准、可回测的科学。

### 1.4 命名体系

| 用途 | 名称 |
|---|---|
| 中文品牌 | 商奕 |
| 英文/拼音 | ShangYi |
| CLI 命令 | `shangyi` |
| 代码仓库 | `shangyi-agent` |
| 比赛项目名（备选，纯中文防校验失败） | 商奕——基于博弈论的企业决策咨询智能体 |

> ⚠️ 申报系统警告英文字母/特殊字符可能导致校验失败，且项目名称提交后不可修改。建议申报用纯中文版本（不含"AI agent"字样）。

### 1.5 两条铁律（贯穿所有设计）

1. **LLM 不算数**：所有数值计算（均衡求解、仿真、统计、绘图）在 Python sandbox 中执行；LLM 只负责建模、调度、解读。报告中每个数字必须有代码/数据出处（provenance 溯源字段）。
2. **关键假设必须过 checkpoint**：payoff 参数、对手估计等硬假设，须经用户确认或标注来源后方可进入模型。

### 2.1 架构图

```
┌────────────────────────────────────────────────────────────┐
│  CLI 交互层（shangyi）                                       │
│  引导式对话 · 假设 checkpoint · 偏好校准 · 进度展示            │
├────────────────────────────────────────────────────────────┤
│  Agent 核心循环（plan → act → observe → reflect）             │
│  会话状态机 · 剧本调度 · 上下文管理                            │
├──────────┬──────────┬───────────────┬──────────────────────┤
│  工具层    │  博弈引擎  │  情报层         │  知识库/案例库        │
│  (Tool    │  GameSpec │  公开数据抓取    │  理论库(RAG)         │
│  Registry)│  求解器    │  信息抽取       │  案例库+回测         │
│  websearch│  均衡选择  │  参与者画像     │  参数先验库           │
│  ingest   │  引擎      │  贝叶斯类型推断  │                     │
│  sandbox  │  对策生成  │               │                     │
│  kb/case  │  敏感性    │               │                     │
├──────────┴──────────┴───────────────┴──────────────────────┤
│  报告生成器：四层图文报告（图表引擎 → md → PDF/docx）           │
└────────────────────────────────────────────────────────────┘
```

### 2.2 一次咨询的生命周期（数据流）

```
用户描述决策问题
  → [intake] 剧本识别 + 价值网映射（focal/顾客/供应商/替代者/互补者五向扫描 + PARTS 检查）
             + 引导式补全（结构化问答）
  → [intel] 公开数据搜集 → 参与者画像更新（全角色）→ checkpoint①（事实确认）
  → [model] 参与人筛选（直接玩家 players + external_actors）→ GameSpec 构建（参数含不确定性区间）
             → checkpoint②（假设确认）
  → [solve] 均衡枚举 + 精炼 → 解集
  → [select] 均衡选择引擎 → 均衡概率分布 → checkpoint③（结果预览）
  → [recommend] 偏好注入 → 对策 + 敏感性 + 翻转阈值
  → [report] 图文报告生成 → 用户签收
  → [archive] 案例入库（预测留档，供日后回测）
```

三个 checkpoint 均可回退修改；每次 checkpoint 的用户回答全部留档。

## 3. Agent 核心循环

### 3.1 会话状态机

```python
class SessionState(str, Enum):
    INTAKE        = "intake"          # 剧本识别与信息收集
    INTEL         = "intel"           # 公开数据搜集与参与者画像
    MODEL_BUILD   = "model_build"     # GameSpec 构建
    SOLVE         = "solve"           # 均衡枚举+精炼
    SELECT        = "select"          # 均衡选择
    RECOMMEND     = "recommend"       # 对策与敏感性
    REPORT        = "report"          # 报告生成
    ARCHIVED      = "archived"        # 已归档
```

状态转移由剧本（Playbook）驱动；LLM 在每个状态内决定调用哪些工具、何时请求 checkpoint。状态与全部中间产物持久化到本地 case 目录（断点续聊）。

### 3.2 剧本（Playbook）机制

剧本 = 某类决策场景的标准作业程序，声明：适用条件、**价值网侧重**（五类参与者的扫描优先级）、intake 问题清单、情报需求、推荐博弈模型、选择器配置、报告模板变量。以 YAML 定义，Agent 可按剧本走，也可在知识库扩展后由 Agent 动态组合（v0.1 先固定剧本，动态组合放 v0.2+）。

**三种咨询模式**（同一引擎栈，入口不同；MVP 三模式均首发接入 `pricing_response` 领域）：

| 模式 | 用户给出 | 系统回答 |
|---|---|---|
| `scenario` 情景分析 | 决策问题背景 | 博弈结构 + 均衡分布 + 对策（§2.2 主流程） |
| `whatif` 决策推演 | 一个具体决策动作（"我降价 15% 会怎样"） | 后果预测：对手反应分布（**含矩阵外非常规反击**）× 各方结果分布（§5.6.1） |
| `discover` 策略发现 | 目标与满意标准（利润≥X、最差损失≤Y） | 满意策略清单 + 帕累托前沿 + 稳健性排序（§5.6.2） |

**MVP 剧本清单（按优先级）**：

| 剧本 | 博弈模型 | 说明 |
|---|---|---|
| `pricing_response` 调价/促销响应 | 差异化 Bertrand + 重复博弈（价格战可维持性） | MVP 首选，数据可得性最好 |
| `competitor_intel` 竞对动向研判 | 不完全信息博弈 + 贝叶斯类型推断 | 参与者画像的独立价值出口 |
| `negotiation` 供应商/渠道谈判 | Rubinstein 议价 + BATNA | |
| `market_entry` 进入/扩张 | 进入威慑 + 空间竞争 | 原"选址"场景并入此剧本 |

### 3.3 LLM 抽象

`shangyi/llm/` 提供 OpenAI 兼容客户端抽象（base_url + api_key 可配），支持 GLM/GPT/Claude 等任意兼容端点切换；LLM 仅承担：剧本路由、问题生成、结构化抽取（JSON mode）、建模建议、聚点判断（受控 prompt）、结果解读与报告文字。**禁止**在 prompt 里要求 LLM 输出任何进入报告的数值。

| `kb_retrieve` | query, top_k | [{doc, section, score}] | 理论库 RAG 检索 |
| `case_store_write/read` | case 对象 | — | 案例库读写 |
| `participant_profile_update` | participant_id, events[] | profile | 参与者画像更新（含贝叶斯后验） |

**搜索/抓取开源组件选型**：搜索后端 [ddgs](https://github.com/deedy5/ddgs)（多引擎聚合 + 自带 MCP server 模式，开发默认）→ 生产自托管 [SearXNG](https://github.com/searxng/searxng)（改善中文覆盖）——**该选型已于 2026-10 反转：SearXNG 已从实现中删除，现行只有博查单后端**（见 Harness D6 的复盘）；正文抽取 trafilatura → 定向深度采集 [Crawl4AI](https://github.com/unclecode/crawl4ai)（自托管 Python 原生）或 [Firecrawl](https://github.com/firecrawl/firecrawl)（开源自托管 + 商业 API）；接线模式参考 duckduckgo-mcp-server / open-websearch（借鉴 schema 与多引擎回退设计，不引入其运行时）；中文质量档可插博查 API。

**sandbox_exec 关键约束**：代码由 LLM 生成但必须经静态校验（白名单 import、禁网络、超时上限）；所有数值结果带 `provenance`（哪段代码、哪个数据文件、哪个工具产出）。

## 5. 博弈建模与求解引擎（核心章节）

**参与者确定（建模第一步）：价值网模型（Value Net）**

依据竞合理论（Brandenburger & Nalebuff, *Co-opetition*），构建 GameSpec 前先做价值网全扫描，解决"这场博弈里都有谁"——避免"只见对手、不见棋盘"：

```
              顾客 Customers
                  ▲
                  │
 替代者 ⇄ 本企业 focal ⇄ 互补者 Complementors    ← 横向：竞争/替代 与 互补合作
                  │
                  ▼
              供应商 Suppliers
```

- **纵向**（价值链上下游）：顾客与供应商——既是议价博弈的对手方，也是价值共创方（竞合）
- **横向**：替代者（substitutors，直接/间接竞争者）与互补者（complementors，生态互补方）
- 五向扫描 → 按本次决策**筛选博弈相关集**：直接玩家入 GameSpec `players`，可被引入的环境方入 `external_actors`（§5.7.2），其余仅入画像库
- 每位参与者建立**参与者画像**（§6.2），按角色差异化画像重点：顾客重支付意愿/需求弹性/集中度，供应商重 BATNA/转换成本/锁定风险，替代者重行为参数，互补者重生态耦合
- **PARTS 检查表**（Players / Added value / Rules / Tactics / Scope，价值网原书的策略五要素）作为 intake 完备性检查，防漏玩家、漏规则、漏附加价值分析
- 价值网图与参与者画像卡为报告②③层标准组件

### 5.1 场景 → 模型映射（知识库第一版内容）

| 场景 | 核心理论组合 | 模型/方法 |
|---|---|---|
| 调价/促销 | 差异化 Bertrand、重复博弈 | 价格战可维持性（触发策略临界贴现因子）、需求交叉弹性估计 |
| 竞对研判 | 不完全信息博弈、信号传递 | 贝叶斯类型推断（清库存型 vs 长期战略型）、信号博弈 |
| 市场进入/扩张 | 进入威慑、空间竞争 | 进入威慑可信度、Hotelling、引力模型 |
| 谈判 | 议价理论 | Rubinstein 轮流出价、纳什谈判解、BATNA 估计 |
| 客户关系/依赖 | 声誉博弈、重复博弈、交易成本 | 合作可维持性、hold-up 风险评估 |
| 横切 | 决策分析、行为经济学、非市场战略 | 决策树、蒙特卡洛不确定性传播、满意化策略（Simon satisficing）、稳健决策（info-gap 稳健满意度）、非市场战略（Baron：监管/舆论/供应链伙伴等环境参与者） |

知识库设计为**开放扩展**：每个理论条目含"适用条件/失效条件/数据需求/输出物"四要素，Agent 建模时检索并引用；发现缺口按同一 schema 扩充（对应"不受限博弈论"的项目约定）。

### 5.2 博弈的统一表示（GameSpec）

```yaml
game_id: case-2026xxxx-pricing
meta: {scenario: pricing_response, playbook: pricing.yaml, created_at: ...}
players:                                # 由价值网筛选而来（§5 参与者确定）
  - {id: focal, name: "本企业", type: focal, vn_role: focal}
  - {id: comp_a, name: "竞争对手A", type: competitor, vn_role: substitutor, profile_ref: opp-comp_a}
strategies:
  focal:  [维持价, 降价10%, 降价20%, 加促销]
  comp_a: [跟随降价, 部分跟随, 不动]
payoffs:
  form: normal            # normal | extensive
  normal:                 # 每个策略组合下各方收益（增量利润，万元）
    # payoff 值不是点估计，而是引用参数表达式
    "[维持价,跟随降价]": {focal: "P1", comp_a: "P2"}
  extensive: null
params:                   # 参数带不确定性分布 → 蒙特卡洛传播
  P1: {expr: "margin*share_hold", dist: normal, mu: 42, sigma: 8, source: "假设A2/用户确认"}
  ...
information: {type: incomplete, types: {comp_a: [dumping, strategic]}}  # 不完全信息时
dynamics: {form: repeated, discount: 0.9, horizon: infinite}
external_actors: []            # 非市场参与者（客户/供应商/监管/交易所/舆论）：
                               # 非直接玩家，可被玩家行动引入并改变支付结构（§5.7.2）
preference: {risk_aversion: 0.7, objective_weights: {profit: 0.6, share: 0.2, cash: 0.2}}  # 用户偏好注入
```

要点：
- payoff 为**参数表达式而非数字**，参数带分布与来源（铁律 2 的落点）；
- 支持标准式与扩展式；重复博弈用 (stage game, discount, horizon) 组合表示；
- v0.1 限定离散策略空间、2–4 个玩家（覆盖 MVP 场景；连续策略（Cournot）走 sandbox 数值求解）。

### 5.3 求解器层（Eval）

1. **枚举**：`nashpy`（双玩家标准式，支持混合均衡）、`python-gambit`（多玩家、扩展式、行为策略）→ 候选均衡集合 E（纯策略 / 混合 / 子博弈完美）。
2. **精炼过滤**：颤抖手完美、序贯理性（gambit 内建）→ E'。
3. **输出**：`EquilibriumSet {equilibria: [{id, type, strategies, expected_payoffs, refined: bool}]}`，进入选择引擎。

### 5.4 均衡选择引擎（Prediction）——算法规格

**统一选择器接口：**

```python
class EquilibriumSelector(Protocol):
    id: str
    def score(
        self, game: GameSpec,
        equilibria: list[Equilibrium],
        profiles: dict[str, OpponentProfile],
    ) -> list[SelectorScore]

@dataclass
class SelectorScore:
    equilibrium_id: str
    weight: float          # 0-1，该选择器认为此均衡出现的相对置信
    rationale: str         # 人类可读理由（进报告）
    evidence: dict         # 机器可审计证据（如收敛轨迹摘要）
```

**内置选择器（v0.1）：**

| id | 方法 | 依据 | 实现要点 |
|---|---|---|---|
| `risk_dom` | 风险占优（Harsanyi–Selten） | 协调博弈经典判据 | 2×2 解析；一般情形用 13 矩阵逼近 |
| `stochastic` | 演化动态 + 随机稳定（KMR/Young） | 长期惯例形成；解释"锁死次优均衡"（价格战陷阱） | replicator dynamics 仿真 + 突变噪声，统计长期占据时间 |
| `learning` | 虚拟对局 / EWA | 有限轮次内实际收敛点 | 按初始信念网格仿真，输出收敛分布 |
| `behavioral` | QRE + level-k | 对手有限理性 | λ 与 k 由对手档案历史行为拟合（见 §6.3） |
| `focal_llm` | 聚点判断（Schelling） | 人类显著性——LLM 独有强项 | 受控 prompt：判断"典型生意人眼中哪个结果 obviously"，输出权重+理由；温度 0；可审计 |
| `persona_sim` | LLM persona 多智能体 rollout（由 §5.7 Swarm 实现） | 行为路径交叉验证 + 非常规行动发现 | 每位玩家（按 GameSpec，不限于对手）一个 persona sub-agent，orchestrator 编排 N 次 rollout + feedback 环，统计落点分布 |

**融合机制：**

```
P(e) = Σ_k  w_k · weight_k(e)   对每个均衡 e 归一化
```

- 权重 `w_k` 初值来自剧本先验配置；
- 案例库回测更新：以"预测分布 vs 实际实现均衡"做 online logistic/Bayesian 更新（对数损失）——**闭环校准，越用越准**；
- 输出按 `persona_sim` 与解析法差异过大时自动告警（提示模型假设或档案可能有误）。

**输出（进报告的核心数字）：**

```json
{
  "equilibrium_distribution": [
    {"eq": "价格战", "prob": 0.60, "drivers": ["stochastic", "behavioral"]},
    {"eq": "默契分层定价", "prob": 0.25, "drivers": ["focal_llm"]},
    {"eq": "先手优势", "prob": 0.15, "drivers": ["learning"]}
  ],
  "confidence": "中等（案例库样本不足，判据先验未校准）",
  "calibration_note": "本案例将进入回测库"
}
```

### 5.5 对策与稳健性（Recommendation）

- **偏好注入**：用户效用 = Σ objective_weights × 各目标收益，风险厌恶对分布做 CVaR 变换后排序；
- **条件策略（博弈树预案）**："若对手 X，则转 Y"——按最可能均衡给主策略，按其余均衡给触发式预案；
- **敏感性/翻转阈值**：蒙特卡洛（参数分布传播）+ one-at-a-time 扫描，回答"利润率估计低到多少时，建议从 A 翻转为 B"。

### 5.6 决策结果预测与满意策略发现（whatif / discover 模式引擎）

#### 5.6.1 条件后果预测（whatif）

输入用户的一个具体决策动作 d（可为策略集内动作，也可为新动作——动态扩入策略空间后求解）：

```
1. 条件子博弈：固定 focal = d，其余玩家自由行动
   → 枚举对手最佳反应集 BR(d)；不完全信息下按对手类型分条件反应
2. 非常规反应生成（开放行动空间，§5.7.1）：对手 sub-agent 与专用提示生成
   "矩阵外"反击候选——投诉对手的客户/供应商、舆论、集体行动、引入监管或交易所等
   新参与者；经三重过滤（合法性 × 弱势方资源可得性 × 激励相容）后注册入 GameSpec
   （含新增 external_actors）并重解
3. 对每个反应 r（常规 + 非常规）：均衡选择引擎在条件子博弈上运行 → P(r | d)
   （复用 §5.4 全部选择器；swarm rollout 仿真多轮反应路径）
4. 重复博弈：沿路径 rollout（触发策略动态）→ 价格战时长、利润恢复期等路径级后果
5. 参数不确定性 Monte Carlo 传播 → 每项后果的 P10 / P50 / P90
```

**输出 ConsequenceReport**：`决策 d → [(对手反应 r, P(r|d), 双方结果分布, 概率驱动判据)]`，直接进报告②层与老板页。

> **设计教训（星宇股份事件，2026-08）**：封闭策略空间的 BR 枚举对弱势方的矩阵外反击结构性失明（详见 §5.7.1），故步骤 2 是 whatif 的必要组成而非可选增强。

#### 5.6.2 满意策略发现（discover，satisficing）

理论根基：Herbert Simon 满意化（satisficing，1978 年诺贝尔经济学奖）——有限理性下不求最优解、求达标解；稳健性参考 info-gap 稳健满意度思想。

```
1. 候选生成：剧本动作模板 × 参数网格（价格档位 / 促销力度 / 时机 / 组合）
   + LLM 依对手档案提议创造性候选（差异化动作、信号性行动）——LLM 只提议，代码评估
2. 逐一后果预测：调用 5.6.1 管线 → 多准则后果分布（利润 / 份额 / 现金流）
3. 满意过滤：各准则"达标概率 ≥ 阈值"（默认 0.6，随偏好校准）→ 满意集
4. 满意集为空时：反馈冲突所在，自动提议抱负水平放宽方案（Simon 抱负水平动态调整）
5. 排序：帕累托前沿 + 稳健满意度（该策略距"结论翻转阈值"的安全余量）
```

**输出 DiscoveryReport**：满意策略清单（≤5 个，含达标概率与最差情形）+ 帕累托图。

**计算量评估**：候选 ≤30 个 × 每候选 Monte Carlo ≤1000 次，本地秒级至分钟级，MVP 可行。

### 5.7 参与者子智能体仿真（Agent Swarm）

**设计决策（用户拍板）**：博弈的直接参与者（对手、供应商、大客户等玩家，按 GameSpec players）各建模为独立 sub-agent（persona），由 orchestrator 编排，主 agent 对 sub-agent 的行动做闭环 feedback。sub-agent 不限于对手——谈判剧本中供应商与大客户同样是 persona；MVP 的 pricing_response 场景仅含替代者对手。Swarm 是 §5.4 中 persona_sim 选择器的架构化升级，承担两项职责：① 选择引擎的行为证据来源；② 非常规（矩阵外）行动的生成器。

```
主 Agent（咨询负责人）
  ├─ Orchestrator（编排器，纯代码）：回合调度 · 终止条件 · 多样性采样
  │    （persona 参数扰动 × N 次 rollout → 行动分布）
  ├─ Sub-Agent：对手A —— persona = 参与者画像 → 角色卡（成本认知/风险偏好/行为风格/历史模式）
  │    输入 game state + 行动历史 → 输出 Move（含矩阵外行动提议 + 理由）
  ├─ Sub-Agent：对手B（同上）
  └─ Sub-Agent（可选，v0.2）：非市场参与者（客户/供应商/监管/舆论的简化反应体）
Feedback 环（主 Agent 执行）：
  rollout 结束 → 审查行动轨迹与参与者画像、博弈论合理性的一致性
  → 偏离则修正 persona 参数并重跑 → 收敛后输出行动分布进选择引擎
```

**接口定义：**

```python
class PersonaSubAgent(Protocol):
    player_id: str
    def act(self, view: GameView, history: list[Move]) -> Move
    # Move = {action: 策略集内动作 | {type: "novel", spec: ...}, rationale: str}

class SwarmOrchestrator(Protocol):
    def rollout(self, game: GameSpec, personas: dict[str, Persona]) -> Trajectory
    def distribution(self, n_rollouts: int, perturb: bool = True) -> ActionDistribution
```

**铁律不变**：sub-agent 可以**提议**行动（含矩阵外），但**评估一律回主引擎**——novel move 注册入 GameSpec 后由解析求解与选择引擎重算后果。Swarm 的输出是行为证据与候选来源，不是结论本身。

#### 5.7.1 非常规反应与弱势方反击（whatif 的必要组成）

设计教训来自星宇股份事件（2026-08，常州星宇批量解约 107 名应届生）：弱势方的致命反击不在原博弈的策略矩阵内——学生向星宇的**客户**（大众等）与**海外供应商**发函投诉、诉至港交所，把新参与者引入博弈、借其 ESG/IPO 声誉激励改变支付结构，最终市值大幅蒸发、H 股 IPO 进程受威胁、公司公开道歉并停职 HR 总监。

机制化解法（已并入 §5.6.1 步骤 2）：

1. **开放行动空间**：sub-agent 的 Move 允许 `type="novel"`——矩阵外行动：投诉对手的客户/供应商、舆论、集体行动、引入监管/交易所
2. **三重过滤**（代码 + LLM 混合）：合法性（法律/平台规则）× 资源可得性（弱势方是否真能执行）× 激励相容（预期收益 > 成本）
3. **注册回 GameSpec**：通过者动态扩入策略空间（含新增 external_actors 参与者节点）→ 重新求解与选择
4. **分工原则**：LLM 想得到（人类非常规反击的模式内化于海量公开案例），解析引擎算得清（后果与概率）——"LLM 不算数"铁律下的正确组合

#### 5.7.2 非市场参与者建模（知识库扩展，"不受限博弈论"约定的实践）

GameSpec 新增 `external_actors` 字段：非直接玩家（客户、供应商、监管、交易所、媒体、公众），平时不行动，但可被玩家行动**引入**并改变支付结构。理论库相应扩展：非市场战略（Baron，市场+非市场一体化策略）、集体行动的逻辑（Olson）、不对称冲突与弱者的武器、声誉与舆论博弈。

| W3 | 选择器 v1 + 融合 + 条件后果预测管线（whatif，含 LLM 非常规反应生成初版）；golden case：已知风险占优/随机稳定结论的博弈，验证选择器方向正确 |
| W4 | pricing_response 剧本（scenario）+ discover 模式 + 价值网映射与参与者画像 + persona sub-agent 最小 Swarm（rollout + feedback 环 + novel moves 三重过滤）+ 偏好校准 + checkpoint |
| W5 | 报告生成器全量图表 + 案例库 |
| W6 | 2–3 个端到端案例（真实/半真实）+ 评审打磨 + 演示脚本（比赛用） |

**质量评估（golden cases）**：① 求解器对已知博弈的正确性单测；② 选择器在文献有明确结论的博弈（如 2×2 协调博弈的风险占优选择、Young 惯例博弈的随机稳定结果）上的方向性验证，以及条件预测 / 满意过滤在构造博弈上的正确性验证；③ 端到端 mock 咨询的专家人工评分表（建模合理性/证据质量/建议可用性/小白可读性 四维）；④ 非常规反应回归测试：以星宇股份事件（2026-08）为原型构造"弱势方 + 压力传导链"案例，验证开放行动空间能产出"向对手客户/监管投诉"类候选并通过三重过滤。

## 12. 风险与对策

| 风险 | 对策 |
|---|---|
| payoff 参数估计质量不足 | 不确定性分布传播 + 翻转阈值显式呈现；先验库标注 borrowed |
| LLM 聚点判断不可靠 | 温度 0 + 理由强制 + 仅作融合判据之一（权重受回测约束） |
| Swarm 仿真发散或成本失控 | rollout 轮数与 LLM 调用预算上限；feedback 环校正 persona；异常分布回退解析选择器 |
| 案例库冷启动无回测 | 置信度分级展示（"先验未校准"），诚实标注 |
| 爬虫合规 | robots.txt、限速、仅公开商业信息、反垄断措辞红线内置模板 |
| 单人开发范围失控 | §11.2 的 out-of-scope 是硬约束 |
