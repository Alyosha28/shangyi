## 1. 项目概述

### 1.1 一句话定位

**商奕**是一个垂直于企业决策领域的 AI Agent（**架构主体用 Rust 编写**，运行时基座 fork-and-trim 自 Codex workspace；产品形态仍对标 Codex / Claude Code，但领域垂直到商业决策咨询）：基于博弈论理论体系但不限于博弈论，为中小企业（欢迎大企业）在市场分析、微观经营决策、竞争对手研判、上下游关系管理等场景中，提供 **eval（评估）→ prediction（预测）→ recommendation（建议）** 的全流程分析，交付图文并茂、博弈论小白可读的咨询报告。

与 v0.1 的"对话式 AI Agent"表述相比，本版明确两点：其一，**harness 不再只是对标对象的类比，而是字面派生自 Codex 的代码基**（Apache-2.0，经裁剪与补丁）；其二，商奕的全部领域逻辑（博弈引擎、均衡选择、情报、知识库、Swarm）均落在自研的 `shangyi-*` crates 中，与基座边界清晰，便于后续替换基座。

### 1.2 目标用户与场景

| 维度 | 设定 |
|---|---|
| 主要客户 | 中小企业主/经营者（无战略部、不懂博弈论）；大企业为高价值延伸客群 |
| 决策场景 | ① 调价/促销等微观决策 ② 竞对动向研判 ③ 市场进入/扩张 ④ 供应商/渠道谈判 ⑤ 客户关系与大客户依赖 |
| 数据假设 | 以公开数据 + 公开数据挖掘为主，用户自有数据（如有）为辅 |
| 交付形态 | 交互式 CLI 咨询过程 → 图文并茂咨询报告（PDF/docx） |

### 1.3 核心差异化（也是比赛技术创新叙事）

**解决多重均衡下博弈模型预测能力缺乏的问题。** 经典博弈论在多均衡博弈（尤其重复博弈，Folk 定理保证均衡无穷多）面前只能给出"都是均衡"，预测力归零。商奕的三层架构：

1. **Eval**：枚举完整均衡解集（含精炼过滤）
2. **Prediction**：均衡选择引擎为每个候选均衡赋"出现概率"（风险占优、随机稳定演化仿真、学习模型、QRE/level-k 行为校准、LLM 聚点判断、persona 仿真，多判据融合）
3. **Recommendation**：结合用户偏好输出对策 + 稳健性分析（结论翻转阈值）

并以**案例库回测闭环**持续校准选择判据权重——把均衡选择从艺术变成可校准、可回测的科学。

### 1.4 命名体系

| 用途 | 名称 |
|---|---|
| 中文品牌 | 商奕 |
| 英文/拼音 | ShangYi |
| CLI 命令 | `shangyi` |
| 代码仓库 | `shangyi`（Rust workspace：`vendor/codex-rs/` + `crates/shangyi-*`；v0.1 的 `shangyi-agent` Python 仓库名不再使用，见 §10） |
| 比赛项目名（备选，纯中文防校验失败） | 商奕——基于博弈论的企业决策咨询智能体 |

> ⚠️ 申报系统警告英文字母/特殊字符可能导致校验失败，且项目名称提交后不可修改。建议申报用纯中文版本（不含"AI agent"字样）。

### 1.5 两条铁律（贯穿所有设计）

1. **LLM 不算数**：所有数值计算（均衡求解、仿真、统计）由**原生 Rust 求解引擎**执行，绘图由进程隔离的 Python 侧车完成；LLM 只负责建模、调度、解读。报告中每个数字必须有代码/数据出处（provenance 溯源字段）。
   *本版修订*：v0.1 的表述是"在 Python sandbox 中执行"。改为 Rust 原生后，数字来自**确定性 Rust 代码**（同一输入必得同一输出、可复现、可审计），而不是 LLM 当下生成的代码——因此这条铁律被**强化**而非放松。沙箱化的代码执行路径仍然保留，但只服务临时的、一次性的数值计算（LLM 写代码 → 静态校验 → fail-closed 独立进程执行），**核心求解与选择路径不经过它**。
2. **关键假设必须过 checkpoint**：payoff 参数、对手估计等硬假设，须经用户确认或标注来源后方可进入模型。

**分层与 v0.1 的对应关系**：v0.1 的横向五格（工具层 / 博弈引擎 / 情报层 / 知识库案例库 / 报告生成器）在本版被重新安置——工具层与 Agent 核心循环**下沉**到 ① 基座层并作为其扩展点暴露；博弈引擎、情报层、知识库案例库**上移**为 ② 引擎层的独立 crate；报告生成器与 CLI **归入** ③ 交付层。概念组件一个没少，只是换了房子。

**来源注记**：① 层为**修改后复用**（Codex `codex-rs`，Apache-2.0，© 2025 OpenAI），其中 `ToolSpec`/`ToolExecutor`/`ToolRouter`（`codex-tools`）与沙箱、审批、provider 抽象为**直接复用**，工具集与指令模板为**修改后复用**；② 层为**自研**；③ 层的 CLI 与报告管线**自研**，`pandoc` 以独立进程调用，绘图由进程隔离的 Python 侧车完成。对 ① 层的设计取舍另有**仅借鉴设计**的部分（不引入其运行时）：DeepSeek Harness（MIT，© 2026 DeepSeek）的事件溯源会话日志、turn/step 词表、整值事件 + 纯投影、fail-closed seam、能力预检与持久子会话描述符。完整对照见 §10 来源注记总表。

### 2.2 一次咨询的生命周期（数据流）

```
用户描述决策问题
  → [intake] 剧本识别 + 价值网映射（focal/顾客/供应商/替代者/互补者五向扫描 + PARTS 检查）
             + 引导式补全（结构化问答）
     基座原语：`PreStep` 钩子注入剧本指引 + 结构化提问工具（`RequestUserInput` 事件）
  → [intel] 公开数据搜集 → 参与者画像更新（全角色）→ checkpoint①（事实确认）
     基座原语：`web_search`/`web_fetch` 工具 + 画像写入 rollout 事件；
               checkpoint 复用审批 seam（`RequestPermissions` 同族的 fail-closed 决策点）
  → [model] 参与人筛选（直接玩家 players + external_actors）→ GameSpec 构建（参数含不确定性区间）
             → checkpoint②（假设确认）
     基座原语：GameSpec 校验工具（`shangyi-tools`，schema 失败即拒绝）+ checkpoint 审批 seam
  → [solve] 均衡枚举 + 精炼 → 解集
     基座原语：`game_solve` 工具（原生 Rust，**不经沙箱**）
  → [select] 均衡选择引擎 → 均衡概率分布 → checkpoint③（结果预览）
     基座原语：`equilibrium_select` 工具 + Swarm 子会话（`spawn_agent` 多 agent）
  → [recommend] 偏好注入 → 对策 + 敏感性 + 翻转阈值
     基座原语：`consequence_predict` / `satisfice_search` / `monte_carlo` 工具
  → [report] 图文报告生成 → 用户签收
     基座原语：`report_render` 工具 + Python 侧车绘图（进程隔离，`python_sidecar_exec`）
  → [archive] 案例入库（预测留档，供日后回测）
     基座原语：rollout 事件落盘（JSONL，序号单调）+ 案例库 projection（整值事件 → 纯投影）
```

三个 checkpoint 均可回退修改；每次 checkpoint 的用户回答全部留档。

**所有阶段跃迁均落日志**：阶段变更、checkpoint 决策、工具调用与其结果都是 harness 会话事件流中的一条记录（JSONL，`seq` 单调），并据此可重建会话的"模型可见表面"。不变量是"**模型可见 ⟺ 已记录**"：凡影响请求的内容（剧本、注入上下文、工具 schema、请求信封）都必须是事件，故任何一次咨询都能被逐事件回放与审计。*来源：该不变量与事件溯源日志**仅借鉴设计**自 DeepSeek Harness（MIT，© 2026 DeepSeek），在 Rust 侧自研实现，不引入其运行时。*

## 3. Agent 核心循环

### 3.1 会话状态机

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum SessionState {
    Intake,       // 剧本识别与信息收集
    Intel,        // 公开数据搜集与参与者画像
    ModelBuild,   // GameSpec 构建
    Solve,        // 均衡枚举+精炼
    Select,       // 均衡选择
    Recommend,    // 对策与敏感性
    Report,       // 报告生成
    Archived,     // 已归档
}
```

状态转移由剧本（Playbook）驱动；LLM 在每个状态内决定调用哪些工具、何时请求 checkpoint。状态与全部中间产物持久化到本地 case 目录（断点续聊）。

**该状态机骑在 harness 的 turn/step 循环之上**：harness 提供 turn（0..n 个 step，step = 一次模型调用 + 它请求的工具执行）这一层的调度与中断/steering 语义；`SessionState` 是商奕叠在其上的**业务阶段**，由剧本显式推进，不参与模型可见对话。三个必须遵守的约束：

1. **不支持的状态跃迁一律失败关闭（fail closed）**：跃迁表由剧本声明（如 `Intake → ModelBuild` 必须存在 `Intel` 阶段的画像事件），未声明的跃迁返回类型化错误并保持原状态，**绝不静默跳到"看起来合理"的下一阶段**——否则报告会带着未确认的假设产出，直接违反铁律 2。
2. **状态持久化为 log-only 事件**：每次跃迁向会话日志追加一条 `session_state_changed` 形态的**整值**事件（携带变更后的完整状态与触发原因），该事件持久、可重放，但**不进入模型转录**（不携带 surface 语义）。恢复会话时由该事件序列折叠出当前状态，因此断点续聊不会静默改变阶段。*来源：log-only / 整值事件 / 纯投影三者**仅借鉴设计**自 DeepSeek Harness（MIT，© 2026 DeepSeek）。*
3. **回退是有向跃迁，不是清零**：checkpoint 回退（如 `Recommend → ModelBuild`）同样走显式跃迁，历史事件保留，使"这份报告是在哪一轮假设下产出的"始终可追。*[推断] 具体跃迁表在 W1 随剧本定义一并确定。*

### 3.2 剧本（Playbook）机制

剧本 = 某类决策场景的标准作业程序，声明：适用条件、**价值网侧重**（五类参与者的扫描优先级）、intake 问题清单、情报需求、推荐博弈模型、选择器配置、报告模板变量。以 YAML 定义，Agent 可按剧本走，也可在知识库扩展后由 Agent 动态组合（本版先固定剧本，动态组合放后续版本）。剧本由 `shangyi-playbooks` 加载，配置分层采用**整行替换**语义（同 `id` 的层条目完全替换该行，绝不深合并），使生效配置可检视、可 diff。*来源：整行替换与配置分层**仅借鉴设计**自 DeepSeek Harness（MIT，© 2026 DeepSeek）。*

**三种咨询模式**（同一引擎栈，入口不同；MVP 三模式均首发接入 `pricing_response` 领域）：

| 模式 | 用户给出 | 系统回答 |
|---|---|---|
| `scenario` 情景分析 | 决策问题背景 | 博弈结构 + 均衡分布 + 对策（§2.2 主流程） |
| `whatif` 决策推演 | 一个具体决策动作（"我降价 15% 会怎样"） | 后果预测：对手反应分布（**含矩阵外非常规反击**）× 各方结果分布（§5.6.1） |
| `discover` 策略发现 | 目标与满意标准（利润≥X、最差损失≤Y） | 满意策略清单 + 帕累托前沿 + 稳健性排序（§5.6.2） |

**MVP 剧本清单（按优先级）**：

| 剧本 | 博弈模型 | 说明 |
|---|---|---|
| `pricing_response` 调价/促销响应 | 差异化 Bertrand + 重复博弈（价格战可维持性） | MVP 首选，数据可得性最好 |
| `competitor_intel` 竞对动向研判 | 不完全信息博弈 + 贝叶斯类型推断 | 参与者画像的独立价值出口 |
| `negotiation` 供应商/渠道谈判 | Rubinstein 议价 + BATNA | |
| `market_entry` 进入/扩张 | 进入威慑 + 空间竞争 | 原"选址"场景并入此剧本 |

### 3.3 LLM 抽象

LLM 抽象由基座的 `codex-api` + `model-provider` 承担（OpenAI 兼容客户端抽象，base_url + api_key 可配），支持任意兼容端点切换；LLM 仅承担：剧本路由、问题生成、结构化抽取（JSON mode）、建模建议、聚点判断（受控 prompt）、结果解读与报告文字。**禁止**在 prompt 里要求 LLM 输出任何进入报告的数值。凭据层为自有的 API key / 环境变量方案（基座的 `login`/`chatgpt`/`keyring-store`/`backend-client`/`analytics`/`cloud-tasks` 等 OpenAI 账号耦合 crate 已移除，见 §10）。

**⚠️ 必做工作项：Chat Completions 适配层。** Codex 派生的基座**只支持 Responses API**：`WireApi` 枚举仅有一个 `Responses` 变体，配置里写 `wire_api = "chat"` 会被**硬报错拒绝**（`CHAT_WIRE_API_REMOVED_ERROR`）。而国内多数目标端点（**GLM/智谱**、**DeepSeek**）主推 **Chat Completions**，不能直接接入。因此本期必须新增适配层，具体落点：

1. **`codex-api` 增加 Chat Completions wire adapter**：把 Responses 形态的请求/事件映射到 `/chat/completions` 的 `messages` / `tools` / `tool_calls` 与流式 chunk，包括 function-call 的参数增量拼接与 `finish_reason` 归一化；
2. **放宽 `model-provider-info` 的 `WireApi`**：允许 `chat` 成为合法值（`model_providers.<name>.wire_api = "chat"`），并为其补上配置校验与文档；
3. 保留"任意 OpenAI 兼容 `base_url`"能力，目标端点仍是 GLM 系（国内合规 + 中文）与 DeepSeek；
4. 适配层必须有差分测试：同一 prompt + 工具集，分别经 Responses 与 Chat 两条 wire 走通工具调用闭环。

**`sandbox_exec` 关键约束（本版修订）**：该工具的**唯一用途**是执行 LLM 临时编写的数值代码，代码必须经静态校验（白名单 import、禁网络、超时上限）；所有数值结果带 `provenance`（哪段代码、哪个数据文件、哪个工具产出）。两条本版强调的边界：

- **核心求解器不经过沙箱。** 均衡求解、选择器数值内核、蒙特卡洛全部是 `shangyi-*` 里的原生 Rust 代码，直接在主进程内以确定性方式执行——沙箱的存在**不是**为了让数字可信，数字的可信性来自"代码是我们自己写的、可复现的"（铁律 1）。
- **fail-closed**：沙箱必须"能强制隔离才执行"。无法隔离时返回类型化错误（`SANDBOX_UNAVAILABLE` 形态）并**拒绝执行**，绝不静默地无隔离运行；且该错误必须与"求解器失败"可区分，避免模型误读。执行形态为**独立短生命周期进程**：无网络、只读根、单个可写临时目录，经 stdin/stdout JSON 通信。*来源：fail-closed seam 的设计**仅借鉴设计**自 DeepSeek Harness（MIT，© 2026 DeepSeek）；隔离原语（Seatbelt / Landlock / bwrap / `execpolicy`）为**直接复用** Codex。*

**`python_sidecar_exec` 许可注记**：侧车经**子进程 + JSON-RPC**（stdin/stdout）通信，**不做进程内 Python 嵌入**（不使用 PyO3 把 CPython 链接进商奕二进制）——这既避免打包/ABI 负担，也避免进程内许可混合。`nashpy`（MIT，© 2016 Vince Knight）**仅**用于 CI 差分测试 oracle，**永不进入发货路径**；绘图用 matplotlib 为 PSF 系许可，安全。理由与替代方案详见 §5.3 的许可合规注记。

## 5. 博弈建模与求解引擎（核心章节）

**参与者确定（建模第一步）：价值网模型（Value Net）**

依据竞合理论（Brandenburger & Nalebuff, *Co-opetition*），构建 GameSpec 前先做价值网全扫描，解决"这场博弈里都有谁"——避免"只见对手、不见棋盘"：

```
              顾客 Customers
                  ▲
                  │
 替代者 ⇄ 本企业 focal ⇄ 互补者 Complementors    ← 横向：竞争/替代 与 互补合作
                  │
                  ▼
              供应商 Suppliers
```

- **纵向**（价值链上下游）：顾客与供应商——既是议价博弈的对手方，也是价值共创方（竞合）
- **横向**：替代者（substitutors，直接/间接竞争者）与互补者（complementors，生态互补方）
- 五向扫描 → 按本次决策**筛选博弈相关集**：直接玩家入 GameSpec `players`，可被引入的环境方入 `external_actors`（§5.7.2），其余仅入画像库
- 每位参与者建立**参与者画像**（§6.2），按角色差异化画像重点：顾客重支付意愿/需求弹性/集中度，供应商重 BATNA/转换成本/锁定风险，替代者重行为参数，互补者重生态耦合
- **PARTS 检查表**（Players / Added value / Rules / Tactics / Scope，价值网原书的策略五要素）作为 intake 完备性检查，防漏玩家、漏规则、漏附加价值分析
- 价值网图与参与者画像卡为报告②③层标准组件

### 5.1 场景 → 模型映射（知识库第一版内容）

| 场景 | 核心理论组合 | 模型/方法 |
|---|---|---|
| 调价/促销 | 差异化 Bertrand、重复博弈 | 价格战可维持性（触发策略临界贴现因子）、需求交叉弹性估计 |
| 竞对研判 | 不完全信息博弈、信号传递 | 贝叶斯类型推断（清库存型 vs 长期战略型）、信号博弈 |
| 市场进入/扩张 | 进入威慑、空间竞争 | 进入威慑可信度、Hotelling、引力模型 |
| 谈判 | 议价理论 | Rubinstein 轮流出价、纳什谈判解、BATNA 估计 |
| 客户关系/依赖 | 声誉博弈、重复博弈、交易成本 | 合作可维持性、hold-up 风险评估 |
| 横切 | 决策分析、行为经济学、非市场战略 | 决策树、蒙特卡洛不确定性传播、满意化策略（Simon satisficing）、稳健决策（info-gap 稳健满意度）、非市场战略（Baron：监管/舆论/供应链伙伴等环境参与者） |

知识库设计为**开放扩展**：每个理论条目含"适用条件/失效条件/数据需求/输出物"四要素，Agent 建模时检索并引用；发现缺口按同一 schema 扩充（对应"不受限博弈论"的项目约定）。

### 5.2 博弈的统一表示（GameSpec）

```yaml
game_id: case-2026xxxx-pricing
meta: {scenario: pricing_response, playbook: pricing.yaml, created_at: ...}
players:                                # 由价值网筛选而来（§5 参与者确定）
  - {id: focal, name: "本企业", type: focal, vn_role: focal}
  - {id: comp_a, name: "竞争对手A", type: competitor, vn_role: substitutor, profile_ref: opp-comp_a}
strategies:
  focal:  [维持价, 降价10%, 降价20%, 加促销]
  comp_a: [跟随降价, 部分跟随, 不动]
payoffs:
  form: normal            # normal | extensive
  normal:                 # 每个策略组合下各方收益（增量利润，万元）
    # payoff 值不是点估计，而是引用参数表达式
    "[维持价,跟随降价]": {focal: "P1", comp_a: "P2"}
  extensive: null
params:                   # 参数带不确定性分布 → 蒙特卡洛传播
  P1: {expr: "margin*share_hold", dist: normal, mu: 42, sigma: 8, source: "假设A2/用户确认"}
  ...
information: {type: incomplete, types: {comp_a: [dumping, strategic]}}  # 不完全信息时
dynamics: {form: repeated, discount: 0.9, horizon: infinite}
external_actors: []            # 非市场参与者（客户/供应商/监管/交易所/舆论）：
                               # 非直接玩家，可被玩家行动引入并改变支付结构（§5.7.2）
preference: {risk_aversion: 0.7, objective_weights: {profit: 0.6, share: 0.2, cash: 0.2}}  # 用户偏好注入
```

要点：
- payoff 为**参数表达式而非数字**，参数带分布与来源（铁律 2 的落点）；
- 支持标准式与扩展式；重复博弈用 (stage game, discount, horizon) 组合表示；
- 本版限定离散策略空间、2–4 个玩家（覆盖 MVP 场景；连续策略（Cournot）走 `sandbox_exec` 的临时数值求解）。

### 5.3 求解器层（Eval）

**本版全部改为原生 Rust 模块**（crate：`shangyi-solver`），发货二进制**零 Python 依赖**：

1. **枚举**（自研算法，见下表）：
   - 支持枚举（support enumeration）：n ≤ 4 玩家标准式，含混合均衡；
   - Lemke–Howson：2 人标准式的互补/不动点路径求解；
   - 扩展式逆向归纳：子博弈完美均衡与行为策略；
   - 重复博弈：以 (stage game, discount, horizon) 表示，枚举触发策略族的可维持条件（临界贴现因子）→ 候选均衡集合 E（纯策略 / 混合 / 子博弈完美）。
2. **精炼过滤**（自研）：颤抖手完美、序贯理性、子博弈完美；退化博弈与多重支撑的边界情形由 CI 差分测试兜住 → E'。
3. **输出**（形状与 v0.1 一致，不改接口）：`EquilibriumSet {equilibria: [{id, type, strategies, expected_payoffs, refined: bool}]}`，进入选择引擎。

**需自研的算法与其 Rust 数值依赖**：

| 用途 | 自研模块 / 算法 | Rust crate（许可） |
|---|---|---|
| 支付矩阵运算、期望收益、混合策略支撑求解 | 期望收益张量收缩、线性系统求解 | `faer`（MIT，首选，纯 Rust 无 C 依赖）/ `nalgebra`（Apache-2.0） |
| LP/MILP 子问题（零和经 LP、相关均衡、最佳反应） | 单纯形/内点经 crate 调用 + 自研建模层 | `microlp`（Apache-2.0，纯 Rust 首选）/ `highs`（MIT 绑定） |
| QRE logit MLE、最佳反应平滑、选择器参数拟合 | 不动点迭代 + 非线性优化 | `argmin`（MIT OR Apache-2.0）；约束形式可加 `clarabel`（Apache-2.0） |
| 蒙特卡洛传播、P10/P50/P90、演化动态仿真 | 分布采样 + 统计量 | `statrs`（MIT）、`rand` / `rand_distr`（MIT OR Apache-2.0） |
| 2 人零和不完全信息扩展式（可选，若需要） | CFR | `cfr`（MIT，唯一维护中的 Rust 博弈求解 crate） |

**Rust 生态的现实（工期风险）**：**Rust 没有维护中的通用纳什均衡求解库。** 除 2 人零和扩展式 CFR（`cfr`）外，支持枚举、Lemke–Howson、虚构对局、复制者动态、QRE、level-k、ESS **全部需要自己写**（约数百行量级，配 `faer` + `microlp`）。这是本版最大的单一工期风险项，已按 **1.5–2 周**预留（见 §11、§12）。

**禁用清单（许可或成熟度原因，不得进入依赖树）**：`lrslib-rs`（**AGPL-3.0-only**）、`lrslib-sys`（AGPL 上游）、`coin_cbc`（传递 CoinOR CBC，**EPL-2.0**，静态链接合规问题）、`amfiteatr*`（crates.io 许可字段为 `non-standard`）、所有 0.x 且近期单次发布的 `game-theory-*` / `extensive-form` / `lau-*`、`nash` / `neumann`（已废弃）。

> **⚠️ 许可合规注记：移除 `python-gambit`（本版最重要的合规修订）**
>
> v0.1 的 §5.3 写的是 `nashpy`（双玩家标准式）+ `python-gambit`（多玩家、扩展式、行为策略）。**本版整体移除 Gambit。**
>
> **理由**：Gambit 及其 Python 绑定 `pygambit` 的许可为 **GPL-2.0-or-later**，且 `COPYING` 即 GPL-2.0 全文——**没有绑定专属许可、没有商业例外**。对闭源商业产品：进程内绑定（`import pygambit` / PyO3 嵌入）会使商奕的二进制成为 GPL 代码的**衍生作品**，必须以 GPL-2.0-or-later 授权，这是不可接受的结果；改用子进程调用可显著降低风险，但**不是**有保证的盾牌，且一旦随产品**分发** Gambit 组件，仍须就该组件履行 GPL 义务（提供完整对应源码、附许可、不限制接收方权利）。对商业产品，**低风险决策就是不用 Gambit**。
>
> **补充事实**：Rust 侧也没有可用的 Gambit 绑定——crates.io 上的 `gambit` 是国际象棋引擎，`gambit-parser` 只解析 `.efg` 扩展式文件且**不求解**，无 `gambit-sys`/FFI。故"多玩家 + 扩展式 + 精炼"的能力改为**自研 Rust 模块**，顺带消除了构建与分发的复杂度。
>
> **处置**：① 求解算法自研（上表）；② `nashpy` 降级为 CI oracle（下段）；③ CI 以 `cargo-deny` 做许可门，白名单外即失败（对齐 Codex 的 `deny.toml` 做法，其依赖树内无 GPL/LGPL/AGPL）。本文档的许可分析为工程调研，**不构成法律意见**；是否引入法务复核见 §13(D10)。

**`nashpy` 的定位（仅 CI 差分测试）**：`nashpy`（**MIT**，© 2016 Vince Knight）保留，但**只作为 CI 的差分测试 oracle**：同一批黄金博弈（教科书博弈 + 随机生成的 2–4 人小博弈）同时喂给 Rust 求解器与 `nashpy`，比对均衡集合（允许置换与等价支撑），出现偏差即 CI 失败。它**进程隔离**（子进程 + JSON）、**永不进入发货路径**、不参与任何报告数值的产生。

### 5.4 均衡选择引擎（Prediction）——算法规格

**统一选择器接口**（语言中立的规格描述，字段与语义与 v0.1 一致；Rust 实现为 `shangyi-selection` 中的 `trait EquilibriumSelector`，数值内核全部原生，不调用 Python）：

```rust
pub trait EquilibriumSelector {
    fn id(&self) -> &str;
    fn score(
        &self,
        game: &GameSpec,
        equilibria: &[Equilibrium],
        profiles: &HashMap<OpponentId, OpponentProfile>,
    ) -> Vec<SelectorScore>;
}

pub struct SelectorScore {
    pub equilibrium_id: String,
    pub weight: f64,          // 0-1，该选择器认为此均衡出现的相对置信
    pub rationale: String,    // 人类可读理由（进报告）
    pub evidence: Value,      // 机器可审计证据（如收敛轨迹摘要）
}
```

**内置选择器（本版）：**

| id | 方法 | 依据 | 实现要点 |
|---|---|---|---|
| `risk_dom` | 风险占优（Harsanyi–Selten） | 协调博弈经典判据 | 2×2 解析；一般情形用 13 矩阵逼近 |
| `stochastic` | 演化动态 + 随机稳定（KMR/Young） | 长期惯例形成；解释"锁死次优均衡"（价格战陷阱） | replicator dynamics 仿真 + 突变噪声，统计长期占据时间 |
| `learning` | 虚拟对局 / EWA | 有限轮次内实际收敛点 | 按初始信念网格仿真，输出收敛分布 |
| `behavioral` | QRE + level-k | 对手有限理性 | λ 与 k 由对手档案历史行为拟合（见 §6.3） |
| `focal_llm` | 聚点判断（Schelling） | 人类显著性——LLM 独有强项 | 受控 prompt：判断"典型生意人眼中哪个结果 obviously"，输出权重+理由；温度 0；可审计 |
| `persona_sim` | LLM persona 多智能体 rollout（由 §5.7 Swarm 实现） | 行为路径交叉验证 + 非常规行动发现 | 每位玩家（按 GameSpec，不限于对手）一个 persona sub-agent，orchestrator 编排 N 次 rollout + feedback 环，统计落点分布 |

**数值内核全部 Rust 原生**（`shangyi-selection`）：`risk_dom`（2×2 解析 + 一般情形 13 矩阵逼近）、`stochastic`（复制者动态 + 突变噪声，`statrs`/`rand`）、`learning`（虚拟对局/EWA 网格仿真）、`behavioral`（QRE logit 不动点 + `argmin` 拟合，level-k 自研）、ESS 谱检查，均为确定性原生代码；只有 `focal_llm` 与 `persona_sim` 需要调用 LLM，且二者的**输出权重经回测约束**。v0.1 中这些算法本已在"自研"范围内，改为 Rust 实现后与铁律 1 更一致：**数值由确定性 Rust 代码产生，而非沙箱中的生成代码**。

**融合机制：**

```
P(e) = Σ_k  w_k · weight_k(e)   对每个均衡 e 归一化
```

- 权重 `w_k` 初值来自剧本先验配置；
- 案例库回测更新：以"预测分布 vs 实际实现均衡"做 online logistic/Bayesian 更新（对数损失）——**闭环校准，越用越准**；
- 输出按 `persona_sim` 与解析法差异过大时自动告警（提示模型假设或档案可能有误）。

**输出（进报告的核心数字）：**

```json
{
  "equilibrium_distribution": [
    {"eq": "价格战", "prob": 0.60, "drivers": ["stochastic", "behavioral"]},
    {"eq": "默契分层定价", "prob": 0.25, "drivers": ["focal_llm"]},
    {"eq": "先手优势", "prob": 0.15, "drivers": ["learning"]}
  ],
  "confidence": "中等（案例库样本不足，判据先验未校准）",
  "calibration_note": "本案例将进入回测库"
}
```

### 5.5 对策与稳健性（Recommendation）

- **偏好注入**：用户效用 = Σ objective_weights × 各目标收益，风险厌恶对分布做 CVaR 变换后排序；
- **条件策略（博弈树预案）**："若对手 X，则转 Y"——按最可能均衡给主策略，按其余均衡给触发式预案；
- **敏感性/翻转阈值**：蒙特卡洛（参数分布传播）+ one-at-a-time 扫描，回答"利润率估计低到多少时，建议从 A 翻转为 B"。数值全部为 **Rust 原生**（`monte_carlo` / `shangyi-consequence`）：相比 v0.1 的 Python（numpy/scipy）估计，同规模扫描无解释器与进程开销、无 GIL，单案例级别的传播与阈值扫描**更快、内存更可控**，且因代码固定而**风险更低**（结果可复现、可审计，不依赖当次生成代码）。*[推断] 具体加速比需在 W3 用黄金案例实测后回填。*

### 5.6 决策结果预测与满意策略发现（whatif / discover 模式引擎）

#### 5.6.1 条件后果预测（whatif）

输入用户的一个具体决策动作 d（可为策略集内动作，也可为新动作——动态扩入策略空间后求解）：

```
1. 条件子博弈：固定 focal = d，其余玩家自由行动
   → 枚举对手最佳反应集 BR(d)；不完全信息下按对手类型分条件反应
2. 非常规反应生成（开放行动空间，§5.7.1）：对手 sub-agent 与专用提示生成
   "矩阵外"反击候选——投诉对手的客户/供应商、舆论、集体行动、引入监管或交易所等
   新参与者；经三重过滤（合法性 × 弱势方资源可得性 × 激励相容）后注册入 GameSpec
   （含新增 external_actors）并重解
3. 对每个反应 r（常规 + 非常规）：均衡选择引擎在条件子博弈上运行 → P(r | d)
   （复用 §5.4 全部选择器；swarm rollout 仿真多轮反应路径）
4. 重复博弈：沿路径 rollout（触发策略动态）→ 价格战时长、利润恢复期等路径级后果
5. 参数不确定性 Monte Carlo 传播 → 每项后果的 P10 / P50 / P90
```

**输出 ConsequenceReport**：`决策 d → [(对手反应 r, P(r|d), 双方结果分布, 概率驱动判据)]`，直接进报告②层与老板页。

> **设计教训（星宇股份事件，2026-08）**：封闭策略空间的 BR 枚举对弱势方的矩阵外反击结构性失明（详见 §5.7.1），故步骤 2 是 whatif 的必要组成而非可选增强。

#### 5.6.2 满意策略发现（discover，satisficing）

理论根基：Herbert Simon 满意化（satisficing，1978 年诺贝尔经济学奖）——有限理性下不求最优解、求达标解；稳健性参考 info-gap 稳健满意度思想。

```
1. 候选生成：剧本动作模板 × 参数网格（价格档位 / 促销力度 / 时机 / 组合）
   + LLM 依对手档案提议创造性候选（差异化动作、信号性行动）——LLM 只提议，代码评估
2. 逐一后果预测：调用 5.6.1 管线 → 多准则后果分布（利润 / 份额 / 现金流）
3. 满意过滤：各准则"达标概率 ≥ 阈值"（默认 0.6，随偏好校准）→ 满意集
4. 满意集为空时：反馈冲突所在，自动提议抱负水平放宽方案（Simon 抱负水平动态调整）
5. 排序：帕累托前沿 + 稳健满意度（该策略距"结论翻转阈值"的安全余量）
```

**输出 DiscoveryReport**：满意策略清单（≤5 个，含达标概率与最差情形）+ 帕累托图。

**计算量评估（本版修订）**：候选 ≤30 个 × 每候选 Monte Carlo ≤1000 次。数值内核为 **Rust 原生**，无 Python 解释器启动与进程往返开销、无 GIL 串行化，故 v0.1 的"本地秒级至分钟级"估计**只会更优**（同硬件下采样吞吐更高、内存峰值更低）；这也是 whatif/discover 两模式能在 MVP 内做成的原因之一。*来源：Rust 数值栈 `faer`/`microlp`/`statrs` 均为纯 Rust 无 C 依赖，构建与分发摩擦更低。*

### 5.7 参与者子智能体仿真（Agent Swarm）

**设计决策（用户拍板）**：博弈的直接参与者（对手、供应商、大客户等玩家，按 GameSpec players）各建模为独立 sub-agent（persona），由 orchestrator 编排，主 agent 对 sub-agent 的行动做闭环 feedback。sub-agent 不限于对手——谈判剧本中供应商与大客户同样是 persona；MVP 的 pricing_response 场景仅含替代者对手。Swarm 是 §5.4 中 persona_sim 选择器的架构化升级，承担两项职责：① 选择引擎的行为证据来源；② 非常规（矩阵外）行动的生成器。

```
主 Agent（咨询负责人）
  ├─ Orchestrator（编排器，纯代码）：回合调度 · 终止条件 · 多样性采样
  │    （persona 参数扰动 × N 次 rollout → 行动分布）
  ├─ Sub-Agent：对手A —— persona = 参与者画像 → 角色卡（成本认知/风险偏好/行为风格/历史模式）
  │    输入 game state + 行动历史 → 输出 Move（含矩阵外行动提议 + 理由）
  ├─ Sub-Agent：对手B（同上）
  └─ Sub-Agent（可选，后续版本）：非市场参与者（客户/供应商/监管/舆论的简化反应体）
Feedback 环（主 Agent 执行）：
  rollout 结束 → 审查行动轨迹与参与者画像、博弈论合理性的一致性
  → 偏离则修正 persona 参数并重跑 → 收敛后输出行动分布进选择引擎
```

**接口定义**（规格描述；Rust 实现为 `shangyi-swarm` 的 `trait PersonaSubAgent` / `SwarmOrchestrator`）：

```rust
pub trait PersonaSubAgent {
    fn player_id(&self) -> &str;
    async fn act(&self, view: &GameView, history: &[Move]) -> Move;
    // Move = { action: 策略集内动作 | Novel { spec: .. }, rationale: String }
}

pub trait SwarmOrchestrator {
    async fn rollout(&self, game: &GameSpec, personas: &PersonaSet) -> Trajectory;
    async fn distribution(&self, n_rollouts: u32, perturb: bool) -> ActionDistribution;
}
```

**基础设施复用（本版新增）**：Swarm **不再自建子智能体编排**，而是复用基座的多智能体设施——`spawn_agent`（及 v2 的 `send_message`/`wait_agent`/`close_agent` 族）、`agent-graph-store`（父子拓扑存储）、`AgentRoleConfig`（角色卡配置）、以及 turn/step 级的中断与 steering 语义。商奕只在其上加两样东西：① persona 的**领域角色卡**（由 §6.2 参与者画像生成）；② 编排器的**回合调度、终止条件与多样性采样**策略。

**capability 预检必须响亮失败（fail loud）**：*来源：**仅借鉴设计**自 DeepSeek Harness（MIT，© 2026 DeepSeek）的子智能体 seam。* 在委派任何 persona 之前，先校验所选 provider/模型--角色组合是否支持所需能力（persona 覆盖、工具白名单、输出 schema、递归深度上限）；**不支持即返回类型化错误，绝不静默降级**。原因很直接：若"对抗性监管者"persona 因后端不支持而被静默忽略、退化成"乐于助人的助手"，仿真结论就是**错的**——而这种错误在报告里看不出来。同理，**递归深度必须持久化**（写入会话 header 而非仅存运行时），否则崩溃恢复后的 Swarm 会把递归预算重置，重组出一批与崩溃前不同的 persona。persona 的**可续子会话**（continuable children）与**持久描述符**亦借鉴 dsh 的对应设计，使 Swarm 崩溃后能恢复**同一批 persona**，而不是意外重组过的 persona。

**铁律不变**：sub-agent 可以**提议**行动（含矩阵外），但**评估一律回主引擎**——novel move 注册入 GameSpec 后由解析求解与选择引擎重算后果。Swarm 的输出是行为证据与候选来源，不是结论本身。

#### 5.7.1 非常规反应与弱势方反击（whatif 的必要组成）

设计教训来自星宇股份事件（2026-08，常州星宇批量解约 107 名应届生）：弱势方的致命反击不在原博弈的策略矩阵内——学生向星宇的**客户**（大众等）与**海外供应商**发函投诉、诉至港交所，把新参与者引入博弈、借其 ESG/IPO 声誉激励改变支付结构，最终市值大幅蒸发、H 股 IPO 进程受威胁、公司公开道歉并停职 HR 总监。

机制化解法（已并入 §5.6.1 步骤 2）：

1. **开放行动空间**：sub-agent 的 Move 允许 `type="novel"`——矩阵外行动：投诉对手的客户/供应商、舆论、集体行动、引入监管/交易所
2. **三重过滤**（代码 + LLM 混合）：合法性（法律/平台规则）× 资源可得性（弱势方是否真能执行）× 激励相容（预期收益 > 成本）
3. **注册回 GameSpec**：通过者动态扩入策略空间（含新增 external_actors 参与者节点）→ 重新求解与选择
4. **分工原则**：LLM 想得到（人类非常规反击的模式内化于海量公开案例），解析引擎算得清（后果与概率）——"LLM 不算数"铁律下的正确组合

#### 5.7.2 非市场参与者建模（知识库扩展，"不受限博弈论"约定的实践）

GameSpec 新增 `external_actors` 字段：非直接玩家（客户、供应商、监管、交易所、媒体、公众），平时不行动，但可被玩家行动**引入**并改变支付结构。理论库相应扩展：非市场战略（Baron，市场+非市场一体化策略）、集体行动的逻辑（Olson）、不对称冲突与弱者的武器、声誉与舆论博弈。

| ② 情景推演 | 经营层 | 博弈树、支付矩阵热力图、演化动态图、条件策略预案表 |
| ③ 参与者画像与证据 | 经营层 | 价值网全景、各参与者画像卡（对手/顾客/供应商/互补者）、时间线、参数估计、来源与可信度 |
| ④ 技术附录 | 懂行者/大企业战略部 | 模型设定、均衡解、选择判据明细、敏感性、假设清单 |

### 9.2 图表清单（matplotlib 侧车统一产出）

价值网全景图 / 参与者画像卡 / 支付矩阵热力图 / 博弈树（graphviz）/ 均衡概率分布（条形）/ 反应曲线 / replicator 相图 / 敏感性龙卷风图 / 翻转阈值曲线 / 参与者事件时间线。

**分工（本版修订）**：**数据序列由 Rust 计算**（`shangyi-report` 产出 JSON/CSV 的 series + 图元规格），**渲染由进程隔离的 Python 侧车完成**（matplotlib；graphviz 经外部进程）。即"算在 Rust、画在 Python"——这样既拿到 matplotlib 的生态便利与中文排版成熟度，又不把任何数值计算移出确定性路径。侧车经 `python_sidecar_exec` 调用（子进程 + JSON-RPC，无进程内嵌入）。

### 9.3 输出管线

markdown（含图）→ pandoc → PDF（含中文字体配置）与 docx。模板文件由 `shangyi-report` crate 装载并渲染（`shangyi/crates/shangyi-report/templates/*.md`；v0.1 的 Jinja2 模板改由 Rust 模板层实现），模板变量即 9.1 各层内容块。

**pandoc 许可注记**：`pandoc` 为 **GPL-2.0-or-later**。商奕**以独立进程调用** pandoc（普通 CLI/管道/文件通信），在主流的"separate programs"立场下，这**不使商奕成为 pandoc 的衍生作品**，商奕自身仍可闭源。但须注意两点：① 若**再分发** pandoc（例如在安装器中捆绑其二进制），则就 *pandoc 本身* 触发 GPL 义务（提供完整对应源码或书面要约、附许可、不限制接收方的 GPL 权利）——**该义务只及于 pandoc 本身**，可作为聚集体与商奕一同分发；更省事的做法是**要求用户自行安装** pandoc，从而完全避免再分发。② 不得把 pandoc 的代码搬运进商奕代码库。LaTeX（TeX Live，LPPL 1.3c）同理：子进程调用无碍。

**图表许可注记**：图形由进程隔离的 Python 侧车渲染（**matplotlib**，PSF 系许可，宽松），而**数据序列由 Rust 计算**后传入——侧车只做绘图，不产生报告数值。

**质量评估（golden cases）**：① 求解器对已知博弈的正确性单测；② 选择器在文献有明确结论的博弈（如 2×2 协调博弈的风险占优选择、Young 惯例博弈的随机稳定结果）上的方向性验证，以及条件预测 / 满意过滤在构造博弈上的正确性验证；③ 端到端 mock 咨询的专家人工评分表（建模合理性/证据质量/建议可用性/小白可读性 四维）；④ 非常规反应回归测试：以星宇股份事件（2026-08）为原型构造"弱势方 + 压力传导链"案例，验证开放行动空间能产出"向对手客户/监管投诉"类候选并通过三重过滤；⑤ **求解器差分测试**：黄金博弈集上 Rust 求解器与 `nashpy`（MIT，CI only）比对均衡集合（允许置换与等价支撑）；⑥ **许可门**：CI 跑 `cargo-deny` 校验 `deny.toml` 白名单，白名单外许可即失败；同时校验分发物含 `LICENSE`/`NOTICE`/`VendorPatches.md`（**NOTICE 与归属声明随包发布**）。

## 12. 风险与对策

| 风险 | 对策 |
|---|---|
| payoff 参数估计质量不足 | 不确定性分布传播 + 翻转阈值显式呈现；先验库标注 borrowed |
| LLM 聚点判断不可靠 | 温度 0 + 理由强制 + 仅作融合判据之一（权重受回测约束） |
| Swarm 仿真发散或成本失控 | rollout 轮数与 LLM 调用预算上限；feedback 环校正 persona；异常分布回退解析选择器；persona 能力预检 fail loud（不支持的 persona 不得静默降级） |
| 案例库冷启动无回测 | 置信度分级展示（"先验未校准"），诚实标注 |
| 爬虫合规 | robots.txt、限速、仅公开商业信息、反垄断措辞红线内置模板 |
| 单人开发范围失控 | §11.2 的 out-of-scope 是硬约束 |
| **求解器许可合规（Gambit GPL）** | **移除 `python-gambit`**（GPL-2.0-or-later，无绑定例外，对闭源商业产品不可接受）；求解器**自研 Rust**；`nashpy`（MIT）仅作 CI oracle 且进程隔离；CI 以 **`cargo-deny` 做许可门**（白名单外即失败，对齐 Codex `deny.toml`）；`deny.toml` 明确禁用 `lrslib-rs`(AGPL)、`coin_cbc`(EPL-2.0)、`amfiteatr*`(non-standard) |
| **Rust 生态无现成博弈求解库** | 支持枚举 / Lemke–Howson / QRE / level-k / ESS **全部自研**，是最大单一工期风险；缓解：**`nashpy` 差分测试** + 教科书博弈**黄金用例**；**预留 1.5–2 周**；把博弈规模限制在 2–4 人离散策略以避开退化/大规模算法缺口 |
| **Codex 仅支持 Responses API** | GLM/智谱与 DeepSeek 为 Chat 系端点，不能直连；**Chat Completions 适配层为本期必做**（`codex-api` wire adapter + 放宽 `model-provider-info::WireApi`），并有双 wire 差分测试 |
| **上游 Codex 变更速度快** | 版本号仍为 `0.0.0`、频繁重命名（如 `ConversationManager`→`ThreadManager`、`TaskStarted` 别名 `TurnStarted` 等）；对策：**vendor 固定 commit**，逐补丁记录于 `VendorPatches.md`（含显著变更声明），**定期 rebase 评估**而非跟随上游；补丁面越小越好 |
| **商标风险** | Apache-2.0 §6 不授予商标权；**不得使用 Codex / OpenAI / ChatGPT 名称**，产品与二进制重命名为 `shangyi`，文档不暗示背书 |
