**日期**：2026-09-17
**状态**：历史基线（Gate A→B 已批准，现由 DSH + Magpie 多智能体协同推进）
**配套**：《商奕 Agent Harness 设计文档 v0.1》《商奕-系统设计文档 v0.2》

---

## 0. 一句话

**用一条有界的自动化循环，把"写代码之前必须先确定的未知量"逐个清掉，并且让循环自己在写代码之前停下来等人放行。**

循环当前只做 Phase A：核实未决事实、产出规格与黄金用例 —— 全部是**只读**或只写 `research/`、`.shangyi-loop/`。**它不能自己授权写源码。**

---

## 1. 为什么是循环，以及为什么是"动态"

### 1.1 上一轮的编排是静态的

产出那两份设计文档时，编排方式是**事先定好角色**：3 个研究 agent（Codex / dsh / 求解器许可），汇合后 3 个写作 agent（前 8 章 / 后 7 章 / v0.2 修订），然后我自己收口。角色、波次、图，都在开工前确定。这适合"目标已知、产物形态已知"的活。

### 1.2 本轮的活不一样

W1 要清的是**未知量**：某件事到底是不是这样、某个许可证到底是什么、上游源码的合并语义究竟是哪种。这类工作的特点是 **下一个动作取决于上一个答案**：

- A2（Codex 配置合并语义）若查明是**深合并**，则 §13.4 的整行替换设计需要一处例外清单；若是**整行替换**，设计不动。
- A1（`codex-core` 是否已发布）若**已发布**，可以当库引用、vendor 树大幅收缩；若**未发布**，必须整 workspace vendor —— 这是两种完全不同的工程路径。
- 许可证核实的结论会**直接改写** §4.5 的白名单和 §15 的模板/图形选型。

所以图的形状在开工时是**不知道的**，它会随着答案生长。静态流水线在这里会做无用功或漏掉分叉。

### 1.3 静态 vs 动态

| 维度 | 上一轮（静态） | 本轮（动态） |
|---|---|---|
| 角色 | 开工前定死 | 调度器按**工作项类型**在运行时选 |
| 波次 | 固定两波 | 波次由上一轮的**发现**决定 |
| 工作图 | 静态、封闭 | **会生长**：验证失败 → 生成新工作项 |
| 终止 | 我判断"写完了" | 显式停止条件 + 预算 + 门 |

**"动态"的确切含义**（避免空话）：输入是工作项声明的**验收标准**，输出是**角色集合与派发顺序**；当验证判定为 `reject` 时，不是重试同一个角色，而是**生成新的工作项**去补那个缺口。图因此生长。

## 2. 拓扑：控制平面 + 执行平面

刻意分成两层，因为"让 agent 决定一切"是不可审计、不可恢复、会跑飞的。

```
┌─────────────────────────────────────────────────────────────┐
│ 控制平面（确定性 · 无模型 · 可审计 · 可恢复）                  │
│   tools/loop/queue.py  +  .shangyi-loop/queue.json          │
│   职责：算可派发集 · 强制 touch 互斥 · 记账 · 查门与预算        │
└─────────────────────────────────────────────────────────────┘
                          ↓ 只读：给我 dispatch plan
┌─────────────────────────────────────────────────────────────┐
│ 编排器（主 agent · 每周转一次）                                │
│   LOAD → DISPATCH → VERIFY → SETTLE → GATE → CHECKPOINT      │
└─────────────────────────────────────────────────────────────┘
                          ↓ 动态选择角色并派发
┌─────────────────────────────────────────────────────────────┐
│ 执行平面（多 agent · 按工作项类型动态选角色）                   │
│   researcher │ engineer │ verifier │ integrator │ resolver   │
└─────────────────────────────────────────────────────────────┘
                          ↓ 产物 + 验收判定
                  回到控制平面记账 → 图可能生长
```

**为什么控制平面必须没有模型**：预算、门、touch 互斥、停止条件这些是**规则**，不是判断。把它们交给 LLM 等于把刹车交给油门。`queue.py` 不调用任何模型，只做确定性的集合运算与追加写。

## 3. 动态派发决策函数

编排器每轮读 `queue.py ready` 的输出（一个 JSON 计划），逐项决定角色：

| 工作项类型 | 派发角色 | 说明 |
|---|---|---|
| `verify`（核实一个事实） | `researcher` → 独立 `verifier` | 后者只拿到**产物 + 验收标准**，不拿前者的推理过程（防锚定） |
| `spec`（产出规格/设计） | `author` → `verifier` | 规格的验收标准尽量可执行（能否编译、是否覆盖 N 个条目） |
| `implement`（写代码） | `engineer` → `verifier`（跑 `cargo test`/`cargo-deny`） | **Phase B 才解锁** |
| `integrate`（合并多个产物） | `integrator` → `verifier` | 只在有 ≥2 个产物需要合成时出现 |
| `contradiction`（两份产物打架） | `resolver` → `verifier` | **图生长的位置** |
| `blocked-on-human` | 不派发 | 出队，计入 `pending-human`，循环继续做别的 |

**图的生长规则**（本设计的关键）：

```
verdict == reject(reasons)  →  生成新工作项：
    kind     = 依据 reason 推断（缺证据 → verify；缺设计 → spec）
    deps     = [被拒项]
    priority = 被拒项.priority
    attempts = 被拒项.attempts + 1
若 attempts ≥ 2  →  转 blocked-on-human（不再自动重试）
```

**并发安全**：每个工作项声明 `touch: [路径]`。调度器**只并发派发 touch 集互不相交的项**。Phase A 全部只读、各写各的研究文件，因此天然全不相交，可满并发；Phase B 写同一 crate 的项会被自动串行化。这是"确定性控制平面"最实际的一个作用。

## 4. 角色清单

| 角色 | 权限 | 产出 | 用于 |
|---|---|---|---|
| `researcher` | 只读（WebFetch/grep/读文件） | 一份带**原文引用**的核实报告 | `verify` |
| `verifier` | 只读 | 逐条对照验收标准的判定：`accept`/`partial(gaps)`/`reject(reasons)`；须独立复核至少 1 处原始出处 | 所有类型 |
| `author` | 写 `research/`、`docs/` | 规格 / 设计 / 黄金用例 | `spec` |
| `engineer` | 写指定路径（Phase B） | 代码 + 通过的测试 | `implement` |
| `integrator` | 写指定路径 | 合并后的单一产物 | `integrate` |
| `resolver` | 只读 + 写结论 | 冲突裁决 + 依据 | `contradiction` |

**硬规则：生产者 ≠ 验证者。** 同一个 agent 绝不允许验证自己刚产出的东西。理由与本项目自己的铁律同构 —— 如果 persona 被静默降级会让仿真结论变错，那么让作者自评会让"已核实"这个标签变得毫无意义。

## 5. 门：Gate A→B（人类确认，不可自授权）

这是本设计里最重要的一个安全属性：**循环不能自己决定开始写代码。**

| 门 | 内容 | 通过条件 |
|---|---|---|
| **Gate A** | Phase A 允许的操作 | 只读；写仅限 `research/`、`.shangyi-loop/`、`docs/` |
| **Gate A→B** | 允许开始写源码（`vendor/`、`shangyi/`） | **`.shangyi-loop/gates.json` 中 `gate_ab.approved = true`，由人类填写。** 循环自身无权修改该字段 |
| **Gate B** | Phase B 每轮的操作约束 | 写前对 `touch` 集做快照；写后必须跑通该轮的**可执行验收**（`cargo check`/`cargo test`/`cargo-deny`）；不通过即回滚该轮 |

`queue.py gate` 会检查该字段；未获批准时，任何 Phase B 工作项都不会进入可派发集，且脚本以非零码退出。

**为什么设这道门**：Phase A 的产物是研究报告与规格，错了可以重来，成本是 token。Phase B 的产物是代码，而**这个 workspace 没有版本控制**（本轮实测：不是 git 仓库），改动没有 undo。在拿到"可回滚"之前就让循环自动写代码，是不负责任的。

## 6. 预算与停止条件

| 项 | 值 | 理由 |
|---|---|---|
| 单轮 agent 数 | ≤ 6 | 一轮是原子的，超了就无法在上下文里收口 |
| 单轮并发写 | touch 互斥自动限制 | §3 |
| 单轮新生成工作项 | ≤ 3 | 防止图爆炸式生长 |
| 单项重试 | ≤ 2 次，之后 `blocked-on-human` | 防止在同一个坑里烧预算 |
| 停滞检测 | 连续 2 轮无 `accepted` → 整循环暂停并报告 | 这是最可能的真实失败模式 |
| 自动化上限 | 有限次（见 §9），非无限 | "长时间"不等于"无限" |

**停止条件**（满足任一即停并报告）：

1. 可派发集为空且无 `pending-human` → **Phase A 完成**
2. 剩余项**全部** `blocked-on-human` → 转人工
3. 达自动化运行次数上限
4. 停滞检测触发
5. 门在位但未获批准且只剩 Phase B 项 → 停在 Gate A→B 前等人

## 7. 状态与持久化

```
.shangyi-loop/
├── gates.json          # 门状态（Gate A→B 只能由人类改）
├── queue.json          # 工作图：id/kind/title/acceptance/deps/touch/status/attempts
├── ledger.jsonl        # 追加式账本：每次派发、判定、图生长（只增不改）
├── STATE.md            # 人读状态（每轮重写）
└── runs/
    └── <ts>-iterNN.md  # 每轮报告：派发了谁、判定如何、图长出了什么、下一步
```

**账本只追加、绝不改写** —— 这不是巧合，是刻意与产品自身的铁律同构：商奕要求"模型可见 ⟺ 已记录"，那么推进循环也应当"做过什么 ⟺ 账本里有"。任何一轮都可以由账本重放出来，任何一次判定都能追溯到是谁做的、依据什么。

**快照回滚（Phase B 用）**：无 git 的情况下，Phase B 每轮在写之前把 `touch` 声明的路径复制到 `.shangyi-loop/snapshots/<ts>-iterNN/`。只快照将被写的文件，不做全量备份 —— 所以 `touch` 声明必须诚实，这是 Phase B 的审计点之一。

## 8. 失败模式与对策（诚实清单）

| 失败模式 | 为什么危险 | 对策 |
|---|---|---|
| **验证者也是 LLM，不是真相** | 会积累"看起来对"的产物 | 验收标准**尽量可执行**（能编译、能跑测试、能 diff）优于"另一个 agent 说它对"；不可执行的才退化为人工复核。**黄金用例的期望值必须来自教材/文献，不得由 LLM 自算** —— 否则 oracle 是循环论证 |
| **图爆炸** | 每轮 reject 生 3 项、再 reject 再生 3 项 | 单轮新生成项 ≤3；单项重试 ≤2；停滞检测 |
| **假收敛** | 把 `partial` 记成 `accept` 好让循环前进 | `partial` 不是 `accept`；有 gap 的项不计入"已完成"；门与停止条件都只认 `accepted` |
| **越权写** | 循环在无人看管时改了源码 | Gate A→B 人类确认；`touch` 白名单；未批准时 Phase B 项不可派发 |
| **无法回滚** | workspace 无 git | touch 集快照；建议把 `git init` 列为 D 项（见 §10） |
| **上游漂移** | Codex 是 `0.0.0` 版、重命名频繁 | vendor 固定 commit；每补丁单独文档化（Harness 文档 D8） |
| **预算无声烧掉** | 长时间自动运行 | 有限次自动化 + 每轮报告 + 账本可随时查 |

**这不是一个"会自己把项目做完"的循环。** 它能自动做的是：把未决事实核实掉、把规格写出来、把黄金用例准备好。它不能替代的是：判断某个设计取舍是否值得、以及决定何时开始写代码。

## 9. 环境前置核实（本轮实测）

| 项 | 实测结果 | 影响 |
|---|---|---|
| Rust | `cargo`/`rustc` **1.98.0** | 高于 Harness 文档假设的 MSRV 1.95，**无需降级**；D8 应改钉 `1.98.0` 或稳定版，而非 1.95 |
| git | 2.55.0 可用，但**当前目录不是 git 仓库** | 循环需快照回滚；建议人类决定是否 `git init` |
| Python | 3.13.15 | 侧车可行 |
| `nashpy` | **未安装** | CI 差分 oracle 缺位 → 已列为 Phase A 工作项（需固定版本的 venv） |
| pandoc | 3.11 | 报告管线可行，进程边界调用 |
| 磁盘 | 可用 609 GB | vendor 150-crate workspace 无压力 |

**两条需要人类拍板的新事项**（记入 §10）：
- **D-L1**：是否 `git init`。循环的 Phase B 安全依赖可回滚；快照是降级方案，git 是正解。
- **D-L2**：`rust-toolchain.toml` 钉哪个版本（1.98.0 实测可用 vs 文档原写的 1.95）。

## 11. 与产品铁律的同构

本循环的纪律不是另起一套，而是把商奕自己的两条铁律**套在工程过程上**：

| 商奕的产品铁律 | 循环里的对应物 |
|---|---|
| **LLM 不算数**：数值必须来自代码 | 验收标准尽量**可执行**；黄金用例期望值来自文献而非 LLM 自算；`nashpy` 差分测试作为机器判定 |
| **关键假设必须过 checkpoint**：硬假设须经确认 | **Gate A→B 人类确认**；`blocked-on-human` 是一等状态而非失败 |
| （工程不变量）**模型可见 ⟺ 已记录** | 追加式账本；图生长可重放 |
| （工程不变量）**失败即拒绝，绝不静默降级** | `partial` ≠ `accept`；无批准则 Phase B 不可派发；验证者 ≠ 生产者 |

一个连自己都不遵守这些纪律的循环，没资格替别人产出符合这些纪律的产品。
